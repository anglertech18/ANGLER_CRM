 md files/schema_update.md asks to bring the UAT database (angler_uat_crm) in line with the development database (crm), since dev is the desired/reference schema. UAT holds real data and must not lose it — no DROP TABLE/TRUNCATE/DELETE, backup first, report before executing.

 Sources used for the comparison (all read-only):
 - Dev schema: queried live via Prisma against crm (local MySQL, Windows) — information_schema.columns/statistics/key_column_usage.
 - UAT schema: user-supplied structure-only dump E:\crm\angler_crm\angler_uat_crm.sql (phpMyAdmin export, MariaDB 10.11.14 on Ubuntu 24.04 — case-sensitive table names, unlike dev's Windows MySQL which silently folds table names to lowercase on disk).
 - Prisma source of truth: server/prisma/schema.prisma.

 User confirmed the target approach for the casing mismatch (see Decision below).

 Key Finding: why UAT's casing "worked" and dev's shouldn't be trusted blindly

 ~52 of ~57 Prisma models have no @@map, so Prisma queries them using the exact PascalCase model name (e.g. PlanOfAction, User, Vertical). UAT's tables already use that exact PascalCase — they are not broken relative to schema.prisma. Dev's tables are lowercase purely because Windows MySQL folds/stores names case-insensitively; Prisma's queries still work there only because Windows matches names case-insensitively.

 Decision (confirmed by user): Add explicit @@map("lowercase_name") to every affected model in schema.prisma, pinning the table name so it's no longer OS-dependent, and rename the corresponding UAT tables to lowercase to match. This achieves "UAT looks like dev" while keeping Prisma functional on UAT's case-sensitive server going forward.

 Follow-up required for production: schema.prisma is shared across all environments. Production (angler_crm) currently has PascalCase tables for these same ~52 models (confirmed via DATABASE_CHANGELOG.md's 2026-07-05 entry, which used PascalCase for Vertical/PaymentType/DailyReport/DailyReportEntry). Once @@map is added, deploying this schema to production without an equivalent rename migration will break production the same way the 2026-07-04 baseline migration incident did. This plan produces a companion prod migration file but does not execute it against production.
